# Enterprise Experience Showcase

## 1. A similar distributed system you've built — scale & impact

I built Sonnr (getsonnr.com), a production management platform for a garment factory, using Next.js, TypeScript, and Supabase. The system tracks the full production lifecycle from order intake through cutting, stitching, finishing, and dispatch, with real time visibility into every stage. One factory runs their entire daily operation on it, replacing a workflow that used to live across paper registers, WhatsApp groups, and memory. The platform serves multiple concurrent users across the factory floor, supervisors tracking order progress, floor managers assigning tailors, and dispatch coordinators marking shipments, all pulling from a shared Supabase Postgres database with row level security enforcing who sees what. I leaned heavily on Next.js server actions for the data mutation layer, which gave me colocated, type safe backend logic without maintaining a separate API surface. I designed and built the entire system end to end, from the database schema and RLS policies through the server actions and the frontend components deployed on Vercel. The patterns I used there, role aware data isolation, async state transitions through server actions, and intelligent caching of reference data, directly informed how I approached this document search service.

## 2. A performance optimization with significant impact

On Sonnr, the production dashboard was taking upwards of 4 seconds to load during peak morning hours when the factory had 200+ active orders. The root cause was a cascade of sequential Supabase queries firing from the client, each independently fetching orders, line items, tailor assignments, and stage history before the page could render anything useful. I restructured the entire data access pattern around server actions that consolidated related lookups into single Supabase queries using nested relation fetching, moved the heavy lifting to the server so the client received a ready to render payload, and introduced an in memory cache for reference data like tailor profiles and stage definitions that change maybe once a week. Load time dropped to under 800ms. The factory supervisor who used to wait for the page every morning with his chai stopped mentioning it entirely, which is the best kind of feedback. The optimization also cut our Supabase row reads dramatically, keeping us within plan limits without needing an upgrade.

## 3. A critical production incident you resolved

During a routine update to the tailor assignment flow on Sonnr, I shipped a change that inadvertently cleared tailor information from the UI whenever an order moved to a different production stage. The factory caught it within minutes because supervisors depend on seeing exactly which tailor is handling each piece at a glance. I checked the Supabase table immediately and confirmed the data was completely intact, it was a frontend state management issue where the component was resetting its local state on a stage transition event, wiping the tailor display even though the database still had it. I reverted the commit and redeployed within 20 minutes. For the durable fix, I decoupled the tailor display from the stage transition state entirely and rewired it to source directly from the database through a dedicated server action on every render. Now even if stage logic has bugs, tailor information always reflects the database truth. I also added a validation layer that flags any render where a tailor field would show empty when the underlying record says otherwise, so this class of issue gets caught before it reaches the screen.

## 4. An architectural decision balancing competing concerns

When building Sonnr I faced a decision between using Supabase Realtime subscriptions for every dashboard update versus a simpler polling approach with manual refresh. Realtime would give the factory floor instant visibility into every change the moment it happened. But it introduced complexity around connection management, particularly on the low end Android devices that floor workers carry around, and it pushed our Supabase usage up considerably. I chose a hybrid path. The active production queue that supervisors stare at all day gets realtime subscriptions so they see assignments and stage changes the instant they happen. Everything else, reports, order history, analytics views, uses a 30 second polling interval through server actions that fetch fresh data on a timer. This kept the experience immediate where speed genuinely matters while keeping the system straightforward to reason about and the costs predictable month over month. Six months into daily factory use, nobody has ever asked for faster updates on the non realtime views, which tells me the tradeoff landed exactly where it needed to.

## AI tool usage note

I used Claude Opus 4 throughout this project, primarily for scaffolding boilerplate like the Dockerfile, docker compose configuration, and Pydantic model definitions, as well as generating the initial structure of documentation and test templates. Every architectural decision was mine. The choice of Redis Streams over a heavier message broker, the multi tenancy isolation strategy with per tenant shard routing, the three layer caching design, and the trade off analysis in the production readiness document all came from my own experience building and shipping production systems. I reviewed and edited every line of generated code. In several places I rejected suggestions that added unnecessary complexity for a prototype, for example the tool wanted to wire in a full circuit breaker library and structured retry middleware, which I stripped out because I could not meaningfully exercise those patterns in a demo and they would have made the codebase harder to read without adding real value.
