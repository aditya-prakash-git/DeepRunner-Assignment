# Enterprise Experience Showcase

## 1. A similar distributed system you've built — scale & impact

I built GetSonnr (getsonnr.com), a production management platform for a garment factory, using Next.js and TypeScript with Supabase as the backend. The system handles the full production lifecycle from order intake through cutting, stitching, finishing, and dispatch, with real time status tracking across every stage. One factory uses it daily to manage their entire workflow, replacing a fragmented process that relied on paper logs and WhatsApp messages. The platform serves multiple concurrent users across the factory floor, each interacting with role specific dashboards that pull from a shared Supabase Postgres database. I designed and built the entire system end to end, from the database schema and row level security policies to the Next.js frontend and the deployment pipeline on Vercel. The architectural patterns I used there, tenant aware data isolation, async state transitions, and layered caching, directly informed the design of this document search service.

## 2. A performance optimization with significant impact

On GetSonnr, the production dashboard was taking upwards of 4 seconds to load during peak hours when the factory had 200+ active orders. The bottleneck turned out to be multiple sequential Supabase queries on the client side, each one fetching related data (orders, line items, tailor assignments, stage history) independently. I restructured the data access layer to use Supabase's ability to fetch nested relations in a single query, combined related lookups into server side calls using Next.js API routes, and added an in memory cache for reference data like tailor profiles and stage definitions that rarely change. Load time dropped to under 800ms and the factory supervisor stopped complaining that the dashboard "freezes every morning." That optimization also reduced our Supabase row reads significantly, which kept us within our plan limits without an upgrade.

## 3. A critical production incident you resolved

During a routine update to the tailor assignment flow on GetSonnr, I shipped a change that inadvertently cleared the tailor information from the UI when reassigning an order to a different production stage. The factory noticed within minutes because supervisors rely on seeing which tailor is handling each piece. The tailor data itself was intact in the Supabase table, it was a frontend state management issue where the component was resetting its local state on a stage transition event. I confirmed the data was safe by querying the tailors table directly, then reverted the problematic commit and redeployed within 20 minutes. The durable fix was to decouple the tailor display from the stage transition state entirely and source it directly from the database on every render, so even if stage logic has bugs, tailor information always reflects the database truth. I also added a simple validation check that flags if a tailor field would be rendered empty when the database says otherwise.

## 4. An architectural decision balancing competing concerns

When building GetSonnr I had to decide between a real time subscription model using Supabase Realtime for every dashboard update versus a polling approach with manual refresh. Real time would give the factory floor instant visibility into changes, but it added complexity around connection management, especially on low end Android devices the workers use, and it increased our Supabase usage substantially. I went with a hybrid approach: real time subscriptions only for the active production queue that supervisors watch constantly, and polling with a 30 second interval for everything else like reports, history, and analytics. This kept the experience snappy where it matters most while keeping the system simple and the costs predictable. Six months in, the factory has never asked for faster updates on the non real time views, which tells me the trade off was the right call.

## AI tool usage note

I used Claude Opus 4 throughout this project. I used it primarily for scaffolding boilerplate (Dockerfile, docker compose wiring, Pydantic models), generating the initial structure of documentation, and writing test templates. Every architectural decision, the choice of Redis Streams over a heavier broker, the multi tenancy isolation strategy, the caching layer design, and the trade off calls in the production readiness analysis, came from my own experience building production systems. I reviewed and edited every line of generated code, and in several cases I rejected suggestions that over engineered the prototype (for example, the tool suggested adding a full circuit breaker library and retry middleware, which I trimmed down to keep the prototype focused on demonstrating the core patterns rather than importing complexity I couldn't fully exercise in a demo).
